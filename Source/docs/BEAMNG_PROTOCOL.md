# BeamNG wire protocol

The current mod/Bridge telemetry generation is **43**. It was introduced with V1.41 and is used by the supported V1.43+ release line. Earlier gameplay generations 41 and 42 and their migration-only decoding paths are not supported in the new Bridge.

A project release number can change without modifying its wire protocol. The Bridge checks both wire compatibility and the mod/Bridge release versions and guides the user to `UPDATE_DUALSENSE.exe` if the versions do not match.

**Updater:** V1.43 and later use the unified `UPDATE_DUALSENSE.exe`, which selects the most recent complete stable GitHub Release containing both mod and Bridge ZIPs. The Bridge is updated after verification, while the mod ZIP is staged for manual installation.

**Compatibility JSON:** generated by CI from the current build version and protocol (43), without querying the latest published release. It is an output artifact for the user to put at repository root; CI never pushes it or creates a GitHub Release.

## Mic Mute latch/focus status (Bridge USB and Bluetooth)

The optional Mic Mute status channel uses UDP from BeamNG GE Lua to the local
Bridge (`127.0.0.1:6978`). It is **LED-only** and never changes the DualSense
microphone/audio power configuration:

- `DMB1` (7 bytes): ASCII `DMB1`, version `1`, toggle-mode flag `0|1`,
  physical-latch flag `0|1`. Retained for backwards compatibility.
- `DMB2` (8 bytes): ASCII `DMB2`, version `1`, the same two flags, followed by
  `Engine.isProgramFocused()` as `0|1`. Sent immediately after `DMB1`.

### Mic focus-loss epoch in the existing DSE4 input stream

The Bridge checks the Windows foreground BeamNG process every 250 ms, outside
of the HID reader/writer. On a foreground-to-background transition it increments
a two-bit focus-loss generation counter (modulo 4). The counter is sent in the
previously unused **bits 6–7 of byte 8** of every 30-byte `DSE4` packet. The
existing touchpad mode (bits 4–5) and button/touch flags are unchanged; packet
length and version remain `DSE4`/`4`. A counter change makes the next input
packet immediate. The initial received counter is a baseline, not an event.

The GE Lua extension also checks `Engine.isProgramFocused()`. Either a current
unfocused reading or a new focus-loss generation clears the optimistic Mic
latch and releases its virtual button, without synthesizing an axis-change
command or a new toggle press. Physical presses made while unfocused are not
applied to BeamNG. On returning to foreground, the existing read-only vehicle
state probe determines the correct LED state for supported, unambiguous vehicle
bindings; it does not drive their state. For arbitrary custom bindings without
a readable state, the LED remains OFF/neutral because there is no reliable
feedback indicating that the game retained the action.

The Bridge extinguishes the orange LED on OS-confirmed focus loss even when
BeamNG suspends Lua before its final `DMB2` status packet. Stale Lua packets
cannot re-light it while the process remains unfocused. The existing watchdog
still releases LED ownership after BeamNG exits or the status stream stops
while the game is foregrounded; a short Lua focus/recovery grace period covers
UDP stalls. When process inspection is unavailable, the existing bounded
fallback handles an explicitly reported background state.

This behavior requires a matching rebuilt Bridge and updated BeamNG mod; the
legacy DMB1 packet remains functional but cannot inform an older Bridge of
program focus. It does not promise that the game engine preserves its own
input ActionMap state while focus is lost. A two-bit generation can wrap after
four completely unobserved focus losses; an ordinary 250 ms Bridge sampling
interval makes this unlikely in normal use.

### Vehicle reset / spawn lifecycle

BeamNG's `Ctrl+R` reloads the selected vehicle Lua VM; it can preserve a
vehicle object ID while replacing the action's state. On reset, respawn,
replacement and controlled-vehicle switch, GE invalidates pending read-only
probe replies, releases the virtual Mic button, and neutralizes its manual
latch. A Mic button held through the transition cannot generate a new DOWN
until physically released. No virtual axis set-mode command is fabricated.
For recognized vehicle actions the LED is subsequently reconciled from two
matching readings separated by time. Unknown/custom actions expose no generic
vehicle state and remain explicitly unverified (neutral indicator). The
optional LED-inversion setting still reverses indicator polarity.

The Go Bridge's regular `LED=` diagnostic describes the general light bar,
not the orange Mic Mute LED. A BeamNG game log entry
`MIC_MUTE_LIFECYCLE_SYNC` can confirm a non-neutral latch was cleared.
